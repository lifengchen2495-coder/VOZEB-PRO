# 按次与 Token 积分计费

在后台「财务管理 → 积分规则」按逻辑模型设置价格。已有模型默认沿用按次扣费，升级不会自动启用 Token 计费或修改已有售价。

## 按次

文本每次调用扣基础积分；图片按张数及清晰度倍率，视频按任务及清晰度、时长倍率。此模式可接入按次收费的上游，也可以对按 Token 收费的上游采用固定积分售价。

## 按 Token

当前对文本模型开放，支持包含图片、视频输入的多模态理解调用；图片、视频和音频生成继续按次。支持 OpenAI Chat Completions、Responses、Gemini 与 Anthropic 常见用量格式，以及 SSE / NDJSON 流式用量。自定义协议必须返回兼容的用量字段；仅返回任务 ID 的异步协议需在后台核对最终用量。

配置项：

| 字段 | 单位与含义 |
| --- | --- |
| 输入单价 | 积分 / 百万输入 Token，最多六位小数 |
| 输出单价 | 积分 / 百万输出 Token，最多六位小数 |
| 缓存输入单价 | 积分 / 百万缓存输入 Token；留空沿用输入单价 |
| 每次预扣积分 | 至少 0.01 积分，最多两位小数；不是消费上限 |

售价由运营人员根据上游成本及预期利润填写，系统不会自动同步供应商价格或把人民币、美元费用转换成积分。同一逻辑模型跨渠道调用使用同一套用户售价。所有单价为 0 表示免费结算。

最终积分 = [(总输入 Token − 缓存 Token) × 输入单价 + 缓存 Token × 缓存单价 + 输出 Token × 输出单价] / 1,000,000。

最终费用向上取到 0.01 积分，真实零用量或免费单价不会产生最低消费。OpenAI 的输入已包含缓存，不能再重复加算；Gemini 的思考 Token 计入输出；Anthropic 的缓存创建 Token 按输入单价计算，缓存读取按缓存单价计算。

例如：输入单价 100、输出单价 300、缓存单价 20，调用返回输入 20,000（含缓存 5,000）、输出 2,000，实际消费为 2.20 积分。如果预扣 5 积分，则结算退差 2.80 积分。

### 火山方舟／豆包视频分析

豆包视频分析使用 `doubao-seed-2-0-pro-260215`，在后台归为文本逻辑模型。视频通过 Files API 上传，分析时把 `input_video.file_id` 发送到站内 `/api/ai/system/{channelId}/responses`，由统一代理转发到火山方舟并完成扣费。给实际绑定该豆包模型的逻辑模型启用「按 Token」，即可使用上述规则，不需要额外的豆包计费开关。

系统读取火山响应的 `usage.input_tokens`、`usage.output_tokens`、`usage.input_tokens_details.cached_tokens`。视频和提示词计入上游统计的总输入；缓存是总输入的一部分。`output_tokens_details.reasoning_tokens` 是输出明细，不再额外相加。非流式响应返回前结算；流式响应从 `response.completed` 的 `response.usage` 读取用量后结算。不根据视频大小、时长或文字长度自行估算。

一次复刻任务还可能调用文案规划模型，每次调用按各自逻辑模型的价格分别结算。Files API 的上传、查询和删除未独立接入积分扣费；其是否存在额外上游费用应以供应商账单为准。

官方协议依据（核对日期：2026-09-08）：[视频理解](https://www.volcengine.com/docs/82379/1895586)、[创建 Response](https://www.volcengine.com/docs/82379/1569618)。`web/src/app/api/ai/system/[channelId]/[...path]/doubao-token-billing.integration.test.ts` 使用该响应格式，经过真实站内代理、配置读取和文件钱包验证预扣、结算、流水及余额；仅上游响应和登录上下文使用测试替身，不代表已完成真实账号扣费或 PostgreSQL 联调。

积分与人民币的充值定价建议见 [积分定价方案](points-pricing-options.md)。

## 预扣、结算与退款

调用前检查余额并预扣，优先使用每日积分，再使用永久积分。调用价格、预扣金额、用量和最终费用保存在原消费流水中，管理员后续调价不会改变该调用的价格。

成功返回完整用量后，系统原子结算差额，不增加调用次数。实际费用高于预扣时补扣，余额不足会形成永久积分欠费；后续请求仍需满足可用余额检查。预扣金额应覆盖常见较大请求。每日与全站积分保护检查发生在预扣阶段，不能把预扣当作上游实际费用的硬上限。

失败、断流和取消按原消费记录退款。结算后再退款只退净消费，不重复退已返还的差额。同一消费的重复结算、退款只生效一次。跨日补扣使用永久积分，已过期的每日积分不会转为永久积分。

原消费金额和余额快照不改写，补扣或退差另记一条关联流水。因此核对余额时应合计原预扣、结算差额及退款；用户个人中心同时显示实际费用与输入、输出 Token 明细。

流式调用保持输出；初始响应头表示预扣，流末尾的 `vozeb.billing` 事件表示结算状态。站内规划调用会读取末尾事件更新最终费用。超大终态事件优先保持正文完整传输，最终账目以消费流水为准。

## 缺失用量与待核对

缺失、格式无效或不完整的用量不会当作 0，也不根据文本长度猜测。系统保留预扣并标记待核对。上游成功后若数据库结算暂时失败，保留生成结果及预扣，并记录消费 ID 和用量诊断；超过 1 小时未结算的预扣也进入核对列表。

在后台「财务管理 → 财务流水 → Token 消费待核对」点击加载，根据上游请求记录填写总输入、输出、其中缓存输入 Token，以及账单编号或请求 ID 等核对依据。界面会按原价格预览补退差额，点击「确认结算」后才写入，并保存管理员审计记录。相同用量重试不会重复扣款；已结算或已退款的流水不能改价重算。

## 存储与升级

文件存储和 PostgreSQL 均支持新规则及账目。PostgreSQL 初始化会自动添加 `app_settings.model_billing_rules` 与 `point_records.token_billing`，保留已有配置和流水。备份、恢复及公开模型配置也包含计费规则。
